## SSE contract repair

Before:

```text
Hermes stream transport error
  -> BFF synthesized event: failed
  -> payload status: FAILED
  -> browser interpreted a business terminal failure
  -> local Trip and RESERVED quota actually remained active
```

After:

```text
Hermes stream transport error
  -> BFF emits event: interrupted
  -> no business status is present
  -> job_status_known=false
  -> fallback=POLLING
  -> local Trip activity state remains unchanged
  -> quota remains RESERVED
  -> only a later true terminal status settles quota
```

The two new PostgreSQL cases begin with an upstream `RUNNING` progress event,
interrupt the stream, verify retained `/api/me.active_trip`, then poll:

- later `SUCCESS`: one quota entry transitions `RESERVED -> CONSUMED`
- later `FAILED`: one quota entry transitions `RESERVED -> RELEASED`

Repeated polling performs no second settlement. Neither interrupted stream
contains `event: failed`, `FAILED`, `TIMEOUT`, or `REJECTED`.

## Frontend contract delta

The current read-only `travel-web` inspection found that
`src/services/jobStream.ts` listens only for `progress`, `complete`, and
`failed`; `src/hooks/useJobProgress.ts` falls back after repeated EventSource
errors.

The frontend integration window must:

1. listen for `event: interrupted`
2. parse `stream_state=INTERRUPTED`, `job_status_known=false`, and
   `fallback=POLLING`
3. close the current EventSource
4. enter authenticated polling immediately, without waiting for a repeated
   error threshold
5. keep the current generation UI non-terminal
6. make no quota-refund claim until polling returns `FAILED`, `TIMEOUT`, or
   `REJECTED`

The BFF did not edit the frontend repository.

## Remaining cross-repository blocker

The BFF sends `X-Internal-Credential`, but current `hermes-travel` does not yet
enforce it on the generation endpoint. This remains a separately authorized P6
blocker and was not changed or represented as solved by J0.5.
